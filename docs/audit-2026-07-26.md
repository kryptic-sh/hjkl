# Audit — 2026-07-26

**Project:** hjkl (terminal text editor) **Version:** 0.37.0 **Scope:** whole
workspace, weighted toward `hjkl-fs` (newest code) **Depth:** high

## Verdict

All three gates are green as of this audit:
`cargo clippy --workspace --all-targets` exits 0, `cargo nextest run -p hjkl-fs`
is 100/100, and the nvim oracle is 81/81. The architecture holds up — locking,
allocation caps, atomic writes and the `:w` path are carefully reasoned, and the
prose in `hjkl-fs` is the best in the tree.

The gate being green is also the point. **Three of the four most serious
findings below are silent data-modification or data-corruption bugs that every
gate passes**, because each sits in a gap the tests do not cover: a property
test that only exercises `MotionKind::Char`, a save path whose two other
implementations are correct, and a macro recorder no test types the letter `q`
into.

Ranked, the three that matter most:

- **B1** — recording a macro drops every literal `q`. Recording `i quick <Esc>`
  stores `iuick<Esc>`; replay types the wrong text. Trivially reachable.
- **B2** — TUI `:w` deletes the file's trailing blank line. Open a file ending
  in a blank line, save without editing, and the file shrinks. `--headless` and
  `--embed` get this right; only the TUI is wrong.
- **B3** — `copy_dir_atomic` fails outright on any tree containing a read-only
  file, breaking cross-filesystem trash and anvil installs.

Counts: **14 bugs**, **6 DRY**, **5 YAGNI**.

**On method.** Every finding was verified against source, and the eight marked
_reproduced_ were executed against the real crates in throwaway harnesses (since
deleted; no tracked file was modified). Observed output is quoted verbatim.
Three plausible claims did not survive checking and were dropped or downgraded —
recorded under "Corrections", because a wrong finding costs more than a missing
one. One of them was wrong because a doc comment in this repo describes
behaviour the code does not have (B14).

## 1. Bugs / correctness

### 🔴 B1 (High) — macro recording silently drops every literal `q`

**`crates/hjkl-vim/src/step.rs:174-180`**

```rust
if crate::vim_state::vim(ed).recording_macro.is_some()
    && !crate::vim_state::vim(ed).replaying_macro
    && input.key != Key::Char('q')
    && !pending_was_macro_chord
{
    crate::vim_state::vim_mut(ed).recording_keys.push(input);
}
```

The `input.key != Key::Char('q')` guard is **redundant for its apparent
purpose** and harmful in every other case:

- The recording-stop `q` never reaches here — `begin_step:51-67` returns
  `Err(true)` on it, short-circuiting the step.
- The `q{reg}` start chord is already excluded by `pending_was_macro_chord`
  (`step.rs:69-72`).

So the only `q`s the guard actually removes are **legitimate ones**: a `q` typed
as insert-mode text, and a `q` consumed as a pending operator target (`fq`,
`tq`, `rq`, `mq` — the stop-check at `:53` requires `Pending::None`, so
recording continues through them).

**Reproduced** with the real `hjkl-vim` dispatch path:

```
A: buffer while recording = "quick\n"
A: register a            = "iuick<Esc>"       <-- the q is gone
A: replay @a produced    = "uick\n"

B: cursor after fq       = (0, 1)             <-- fq worked while recording
B: register b            = "0f"               <-- expected "0fq"
```

Case A is the common one: any macro that types a word containing `q` replays
corrupted text. Case B is worse in kind — the recorded `f` has lost its target,
so on replay `f` swallows the _next_ macro keystroke and everything after it
desynchronizes, mutating text at the wrong positions.

`step.rs` is the only recorder on the live path (`dispatch_input` → `end_step`).
Fix: delete the `input.key != Key::Char('q')` clause; the two cases it looks
like it is guarding are already handled upstream.

**Confidence: high** (reproduced end-to-end, and the two upstream short-circuits
were traced).

### 🔴 B2 (High) — TUI `:w` deletes the file's trailing blank line

**`apps/hjkl/src/app/ex_dispatch.rs:1179`** (in `save_slot`, the universal TUI
`:w` path)

```rust
let needs_trailing_nl = !body.is_empty() && !body.ends_with(b"\n");
```

The load path strips exactly one trailing newline
(`apps/hjkl/src/app/mod.rs:803`: `content.strip_suffix('\n')`). So a file
`"x\n\n"` — two lines, the second blank — loads to a rope whose
`content_joined()` is `"x\n"`. The `!body.ends_with(b"\n")` clause then decides
no terminator is needed, and `:w` writes `"x\n"`.

**Open a file whose last line is blank, save it without editing, and the file
gets shorter.**

`--headless` (`apps/hjkl/src/headless.rs:262`) and `--embed`
(`apps/hjkl/src/embed.rs:404`) use the correct condition, `!joined.is_empty()`,
and round-trip. The TUI diverges both from vim and from hjkl's own RPC modes.

**Reproduced** by driving the real `hjkl-buffer` through each of the three
implementations' exact expressions:

```
original "x\n\n"    lines=2  joined="x\n"
   TUI  -> "x\n"      *** CHANGED ***
   head -> "x\n\n"    round-trips

original "a\nb\n\n"  lines=3  joined="a\nb\n"
   TUI  -> "a\nb\n"   *** CHANGED ***
   head -> "a\nb\n\n" round-trips

original "a\nb\n"    lines=2  joined="a\nb"
   TUI  -> "a\nb\n"   round-trips        (unaffected: last line non-blank)
```

Fix: use `!body.is_empty()`, matching headless and embed. Note the write is
recorded as the new `disk_len` baseline, so `checktime` never reports the file
as changed underneath — the shrink is invisible.

A **second, narrower** case falls out of the same reproduction and affects all
three paths: a file containing exactly `"\n"` (one empty line) is written back
as `""`. Same class, much rarer.

**Confidence: high** (reproduced; the three expressions were run against the
real buffer, not paraphrased).

### 🔴 B3 (High) — `copy_dir_atomic` fails on any tree containing a read-only file

**`crates/hjkl-fs/src/dir.rs:162-174`**

```rust
} else if file_type.is_file() {
    std::fs::copy(&src, &dst)?;
    // Flush BEFORE applying the mode, and through a writable handle. ...
    if opts.fsync {
        File::options().write(true).open(&dst)?.sync_all()?;
    }
    apply_file_mode(&dst, opts.mode)?;
```

`std::fs::copy` **already copies the source's permission bits to the
destination**, so by the time the fsync reopen runs, `dst` is `0444` for a
read-only source and `File::options().write(true).open(&dst)` fails `EACCES`.

The comment above it is the tell: it correctly identifies that "a mode applied
first can itself remove write access (a `0444` source becomes a read-only file)"
and orders the flush before `apply_file_mode` to avoid exactly this — but
`apply_file_mode` is not the only thing that sets the mode, and `fs::copy` got
there first. The mitigation does not mitigate. `opts.fsync` is `true` in
`WriteOptions::default()`, so this is the default path.

**Reproduced** through the public API:

```
fsync=true  => Some("Permission denied (os error 13)")
fsync=false => Ok(())                        # same tree, fsync off
cross-device move of TREE with 0444 file => Some("Permission denied (os error 13)")
  source tree still there: true ; dest exists: false
cross-device move of single 0444 FILE => None    # single files are fine
```

Reachable on two paths, both via `move_atomic` → `copy_then_delete` →
`copy_dir_atomic` (the `EXDEV` fallback):

- **Trash** (`crates/hjkl-app/src/trash.rs:109`) — the trash lives under
  `$XDG_CACHE_HOME` and the deleted entry can be anywhere; `trash.rs:84-90`
  names cross-filesystem as the everyday case. Deleting a directory containing
  any read-only file (a `~/.cargo/registry/src` tree is entirely `0444`) fails.
- **Anvil install** (`crates/hjkl-anvil/src/installer.rs:288` via
  `move_dir_cross_device`) — `installer.rs:264-266` states the package tree is
  extracted under the cache root and lands under the data root, "the case this
  exists for". Extracted archives routinely carry `0444` files.

No data loss — the source survives and the destination is not created (verified
above) — but the operation fails hard. Scoping: **tree path only.**
`copy_atomic` sets the mode _inside_ the fill closure, after writing, so single
files are correct (confirmed: `=> None`).

The 100/100 suite has no read-only-file-in-a-tree case, which is why it passes.

**Confidence: high** (reproduced end-to-end through `move_atomic`).

### 🟠 B4 (Medium, latent) — the inverse of a linewise delete of the **last** row does not round-trip

**`crates/hjkl-buffer/src/edit.rs:323-360`** (`do_delete_range`,
`MotionKind::Line`)

In the `lo > 0 && hi == last` branch the span actually removed is `"\n" + lines`
— the **leading** separator (`edit.rs:326`:
`(c.text.line_to_char(lo) - 1, c.text.len_chars())`) — but the recorded inverse
is `InsertStr { at: (lo, 0), text: lines + "\n" }`, with a **trailing**
separator. Replayed against the post-delete buffer, `at: (lo, 0)` refers to a
row that no longer exists, clamps, and inserts in the wrong place.

**Reproduced:**

```
middle row 1: "a\nb\nc" -> delete -> "a\nc"
   inverse = InsertStr { at: row 1, col 0, text: "b\n" }
   inverse applied -> "a\nb\nc"   round-trips

LAST row 2:   "a\nb\nc" -> delete -> "a\nb"
   inverse = InsertStr { at: row 2, col 0, text: "c\n" }
   inverse applied -> "a\nc\nb"   *** CONTRACT VIOLATED ***
```

This breaks the contract stated at `edit.rs:150`: "Pushing the inverse back
through `apply_edit` restores the previous state."

**Why it is latent, and why it will not stay latent.** Undo is rope-snapshot
based, so it does not consume this inverse. The only consumer is
`Editor::edit_at_all_selections` (`crates/hjkl-engine/src/editor.rs:3298`,
`inverses.push(self.mutate_edit(edit))`) — the multicursor path, which is
deliberately kept unwired pending a future vim binding. The day a multicursor
`dd` on the last line lands, this corrupts text.

**Why the gate misses it:** the round-trip property test
(`crates/hjkl-buffer/tests/proptest_roundtrip.rs:87-93`) only ever generates
`MotionKind::Char`. The linewise shape is never exercised.

**Confidence: high** (reproduced).

### 🟠 B5 (Medium) — RPC filesystem confinement is defeated by a symlink; the fix is already in the tree, unwired

**`crates/hjkl-engine/src/policy.rs:50-60`**, consumed at
**`apps/hjkl/src/save.rs:46`** and **`:52`**

```rust
pub fn path_escapes(path: &std::path::Path) -> bool {
    path.components().any(|c| {
        matches!(c, Component::ParentDir | Component::RootDir | Component::Prefix(_))
    })
}
```

Purely lexical. A relative path whose components are all `Normal` passes —
including one traversing a **symlink** out of the working directory. `save.rs`
then canonicalizes (`:52`), following that symlink, and writes to the resolved
target. `--embed`/`--nvim-api` enable this policy precisely because
`apps/hjkl/src/main.rs:527-535` documents those modes as taking paths from an
untrusted caller.

**Reproduced** (cwd `project`, containing symlink `escape` → sibling `outside`):

```
check_fs_path("../outside/secret.txt") -> blocked
check_fs_path("/etc/passwd")           -> blocked
check_fs_path("escape/secret.txt")     -> ALLOWED
canonicalize("escape/secret.txt") = /tmp/.../outside/secret.txt
...which is outside cwd /tmp/.../project: true
hjkl_fs::resolve_under(cwd, "escape/secret.txt") -> blocked (PermissionDenied)
```

The last line is the finding: **`hjkl_fs::resolve_under` already rejects exactly
this** and has zero callers workspace-wide (Y2). It shipped in 0.37.0 for issue
#317 and was never wired to the policy layer it was built for —
`crates/hjkl-fs/src/path.rs:27-29` even names
`hjkl_engine::policy::check_fs_path` as the consumer expected to sit on top of
it. The same gap applies to the read paths
(`crates/hjkl-ex/src/builtins.rs:138`, `apps/hjkl/src/embed.rs:177`).

Severity is Medium, not High, because it needs a symlink pointing outside the
tree to already exist in the working directory — the RPC client cannot create
one through the editor. It is a defence-in-depth layer that does not hold.

**Confidence: high** for the mechanism (executed); **medium** for real-world
impact, which depends on deployment.

### 🟠 B6 (Medium) — runtime `:map` silently mis-parses common vim key notation

**`apps/hjkl/src/app/keymap.rs:147-169`** →
**`crates/hjkl-engine/src/input.rs:118-214`**

`parse_key_sequence` lowercases a **subset** of tags into `decode_macro`'s
case-sensitive spellings and passes the rest through unchanged. `decode_macro`
has no arm for the remainder, so its `_` branch (`input.rs:195-214`) emits the
tag as literal characters. **Observed:**

```
decode_macro(<CR>    ) -> 1 inputs: Enter
decode_macro(<Enter> ) -> 7 inputs: Char('<') Char('E') Char('n') Char('t') Char('e') Char('r') Char('>')
decode_macro(<Return>) -> 8 inputs: ... literal ...
decode_macro(<Escape>) -> 8 inputs: ... literal ...
decode_macro(<Insert>) -> 8 inputs: ... literal ...
decode_macro(<F5>    ) -> 4 inputs: Char('<') Char('F') Char('5') Char('>')
decode_macro(<S-Tab> ) -> 7 inputs: ... literal ...
decode_macro(<C-S-x> ) -> 1 inputs: C-Char('S')          <-- wrong, and silent
```

So `:nmap <Enter> x` binds the seven-character literal sequence `<Enter>`, not
the Enter key; the mapping can never fire. Vim treats `<Enter>`/`<Return>` as
synonyms for `<CR>` and supports `<Escape>`, `<Insert>`, `<F1>`–`<F12>`,
`<S-Tab>`.

The last line is the worst case: `decode_macro`'s `C-` arm takes
`t.chars().nth(2)` (`input.rs:175-184`), so `<C-S-x>` yields **Ctrl+`S`** — not
a literal fallback, not an error, but a _different valid binding_ that can
shadow a real one.

The other parser in the tree handles all of these correctly
(`crates/hjkl-keymap/src/chord.rs:231-259`), which is finding D1:

```
Chord::parse(<Enter> ) -> Ok(Enter)      Chord::parse(<F5>   ) -> Ok(F(5))
Chord::parse(<Insert>) -> Ok(Insert)     Chord::parse(<S-Tab>) -> Ok(Tab + SHIFT)
Chord::parse(<C-S-x> ) -> Ok(Char('x') + SHIFT|CTRL)
```

Existing tests only exercise `<leader>` and `<CR>`
(`apps/hjkl/src/app/tests/keymap.rs:172,1254,1280`) — the supported subset.

**Confidence: high** (both parsers executed and compared).

### 🟠 B7 (Medium) — `viewport_math` dropped the stale-cursor clamp its original had

**`crates/hjkl-engine/src/viewport_math.rs:163-175`** vs
**`crates/hjkl-buffer/src/buffer.rs:396-402`**

The buffer-side original clamps before walking:

```rust
// Clamp against the live rope: another view sharing this Buffer may
// have removed rows since this view's cursor was last clamped, and
// `rope.line(r)` panics past the last line.
let cursor_row = cursor.row.min(c.text.len_lines().saturating_sub(1));
```

The engine relocation does not:

```rust
let cursor_row = cursor.line as usize;
...
for r in top..=cursor_row {
    let line = Query::line(buf, r as u32);   // panics OOB by spec
```

The clamp exists because a per-window cursor goes stale when another view
shrinks the shared `Buffer`; it carries an explicit comment and a named
regression test (`cursor_screen_row_survives_shrink_from_other_view`). The
relocation's module doc claims the move was identical. It was not.

**What I verified:** that the clamp is present in one and absent in the other,
and that `Query::line` panics out of bounds by specification
(`buffer_impl.rs:133-139`, and issue #313).

**What I did not verify:** the concrete crash path. The proposed route is an LSP
`apply_workspace_edit` shrinking a buffer shown in an unfocused split whose
cursor sits near EOF, then focusing that split — `apps/hjkl/src/app/lsp_glue.rs`
has no `rebase_sibling_cursors` call, unlike the keystroke and ex paths. I did
not build that scenario, so treat the crash as plausible-but-unproven; the lost
clamp is fact either way, and restoring it is a two-line change.

**Confidence: high** that the defensive clamp was lost; **medium** on
reachability.

### 🟠 B8 (Medium) — `J` join omits both of vim's no-space exceptions

**`crates/hjkl-vim/src/vim/command.rs:402-407`**

```rust
let separator = if !cur_line.is_empty() && !next_trimmed.is_empty() { " " } else { "" };
```

Vim's `:h J` inserts a single space _except_ when the first line already ends in
whitespace, or the next line starts with `)`. Neither exception is implemented:

- `"foo "` + `"bar"` → `"foo  bar"` (vim: `"foo bar"`)
- `"foo"` + `")x"` → `"foo )x"` (vim: `"foo)x"`)

Reachable from `J`, visual `J` and `:join`.

**Confidence: high** on the code; the vim rules are from `:h J` and were not
confirmed against a live nvim (the oracle cannot drive `:` keys).

### 🟡 B9 (Low–Medium) — hand-rolled temp+rename survived the `hjkl-fs` migration in anvil

**`crates/hjkl-anvil/src/store.rs:223-228`** and **`:365-370`**

```rust
let staging = target.with_extension("rev.tmp");
std::fs::write(&staging, rev.to_string())?;
std::fs::rename(&staging, &target)?;
```

Three defects relative to `hjkl_fs::write_atomic`, which this same crate already
uses elsewhere (`installer.rs:288`, `:313`, `:484`, `:817`):

1. **Fixed staging name** — no pid, no counter. Two anvil processes writing the
   same package's `.rev` clobber each other's staging file mid-write, and one
   can rename the other's partial content into place.
2. **No `fsync`** — the rename can reach disk before the data, so a crash leaves
   a `.rev` naming content never written.
3. **No cleanup on failure** — a failed rename leaves the staging file forever.

Drop-in replacement, and exactly the drift the crate exists to end
(`crates/hjkl-fs/src/atomic.rs:1-8` names seven such implementations; these two
were missed). The tests re-inline the pattern twice more (`store.rs:648-652`,
`:824-828`).

**Confidence: high** (read; the race was reasoned about, not raced).

### 🟡 B10 (Low–Medium) — the non-atomic `:w` fallback truncates first, and two doc sites promise it does not

**`crates/hjkl-fs/src/atomic.rs:154-164`**, echoed at
**`apps/hjkl/src/save.rs:21-25`**

```rust
fn write_in_place<F>(target: &Path, opts: &WriteOptions, fill: &F) -> io::Result<()> {
    let mut file = File::create(target)?;   // O_CREAT|O_TRUNC
    fill(&mut file)?;
```

`File::create` truncates. If `fill` fails partway — ENOSPC being the motivating
case — the file is left truncated and the original content is gone.

Both doc sites claim otherwise. `atomic.rs:38-40`: "Only ever taken when nothing
has been renamed into place, so a mid-write failure is never compounded into
data loss." `save.rs:23-25` repeats it. Both conflate _"the atomic path has
written nothing yet"_ with _"no data can be lost"_. On this branch a mid-write
failure **is** data loss — and it is precisely the failure `save.rs:3-5` says
the module eliminated ("A crash or ENOSPC mid-write can no longer leave the
target truncated the way the old in-place `File::create` could"): true on the
atomic path, false on this one.

A non-atomic fallback is a defensible tradeoff. The finding is that the
guarantee is overstated in two places, so a future reader will trust a property
that does not hold on the cross-device / unwritable-parent path.

Compounding it: **this path has no test coverage.** The only test named for it,
`nonatomic_fallback_writes_when_temp_cannot_be_created` (`atomic.rs:495-504`),
states in its own comment that it takes the _atomic_ path instead.
`write_in_place` is reachable only from `atomic.rs:198` and `:237`, neither of
which any test drives.

**Confidence: high** (`File::create` truncation is documented std behaviour).

### 🔵 B11 (Low, latent) — the lock layer silently satisfies a shared→exclusive upgrade

**`crates/hjkl-fs/src/lock.rs:64-92`**, **`:212-234`**

`acquire_in_process` decides re-entrancy on **thread identity alone**, with no
record of the outer guard's mode. A thread holding a _shared_ lock that calls
`lock_exclusive` gets `FileLock { file: None }` — a guard carrying no OS lock —
while only a **shared** `flock` is held. Cross-process exclusion is silently
lost for the whole inner section.

`lock.rs:61-63` knows this and states the rule ("Taking an _exclusive_ lock
inside a _shared_ one would be an upgrade and is not supported"), but it is
enforced by convention, not by code.

**No current call site violates it** — I enumerated and read every one:
`ex_dispatch.rs:1768` takes the exclusive lock first and documents this exact
reasoning (`:1761-1764`); `swap.rs:301,318` are shared reads nesting under it;
`undofile.rs:160,185,196` and `filestate.rs:297` never nest a write inside a
read. Latent, not live.

Cheap hardening: record the mode in `Holder` and `debug_assert!` on an upgrade,
turning a silent correctness loss into a test failure the first time someone
writes the natural read-then-write sequence.

**Confidence: high** on the mechanism and on "no current caller does it".

### 🔵 B12 (Low) — X11 clipboard accumulates mime formats across copies

**`crates/hjkl-clipboard/src/backend/x11_thread.rs:1029-1036`**

```rust
let data = state.owned.entry(sel_atom).or_insert_with(|| OwnedData { … });
if !data.targets.contains(&mime_atom) { data.targets.push(mime_atom); }

```

Each `set()` carries one mime atom (`x11_thread.rs:968`), but previous atoms

Impact is limited — hjkl's own yanks are text-only, so the same atom is
overwritten — but it is wrong and inconsistent with the rest of the crate.

**Confidence: high** on the code path (read; not run — needs an X server).

### D2 — `km_to_crossterm` is a drifted copy of `hjkl_keymap_tui::to_crossterm`

**`apps/hjkl/src/app/chord_routing.rs:61-93`** vs
**`crates/hjkl-keymap-tui/src/lib.rs:100-131`**

Identical mapping except the library version canonicalizes `Tab`+SHIFT →
`BackTab`, with a comment noting that `Tab`+SHIFT is "the never-emitted" form
that will not round-trip through `from_crossterm`. The copy omits it.

**Both are live**: `chord_routing.rs:102,128` use the copy;
`apps/hjkl/src/app/mod.rs:2969` uses the library one through the
`keymap_translate` shim — whose own doc says "all logic lives in
hjkl_keymap_tui". Replaying an unbound Shift-Tab therefore produces a different
event depending on which path fires. Delete the copy. **Confidence: high.**

### D3 — theme→ratatui style conversion reimplemented in three tui crates

`hjkl-statusline` re-exports the theme types verbatim
(`crates/hjkl-statusline/src/lib.rs:37-40`), so all of these convert the
**same** types:

- `crates/hjkl-theme-tui/src/lib.rs:18-63` — the designated adapter.
- `crates/hjkl-statusline-tui/src/lib.rs:26-64` — the same bold/italic/
  underline/reverse/strikethrough → `RMod` and `Rgb` logic, reimplemented
  without depending on theme-tui.
- One-line color copies at `crates/hjkl-completion-tui/src/lib.rs:84` and
  `crates/hjkl-which-key-tui/src/lib.rs:68`.

`hjkl-theme-tui` has exactly **one** consumer (`hjkl-syntax-tui`). Add a
`Modifiers` flag and statusline-tui's copy silently ignores it. **Confidence:
high.**

### D4 — anvil's hand-rolled atomic writes

Same sites as **B9**. Listed here too because it is the "seven implementations
that drifted" pattern reappearing in a crate that already depends on the seam.
**Confidence: high.**

### D5 — two crossterm→engine key bridges, and the maintained one is the lossier one

- `crates/hjkl-engine-tui/src/lib.rs:34-56` (`crossterm_to_input`) — **live**
  (used by `hjkl_vim_tui::handle_key`). No arms for
  PageUp/PageDown/Insert/BackTab/F-keys; all fall to `_ => Key::Null` and are
  discarded at `crates/hjkl-vim-tui/src/lib.rs:24-27`.
- `crates/hjkl-editor-tui/src/lib.rs:192-231` (`crossterm_key_event_to_input`) —
  the **more complete** twin, with **zero callers outside its own crate**.

The engine does model `Key::PageUp`/`PageDown`
(`crates/hjkl-engine/src/input.rs:24`) and `crates/hjkl-vim/src/insert.rs:179`
handles them, so the live bridge discards keys the layer below implements. **I
could not confirm any user-visible key loss**: the app intercepts
PageUp/PageDown earlier in insert mode
(`apps/hjkl/src/app/event_loop.rs:145-152`), and I did not trace every
normal-mode route. Reported as duplication, not as a bug. **Confidence: high**
on the duplication, **low** on any behavioural consequence.

### D6 (Low value) — bonsai's "publish staging, tolerate a lost race" block, four times

Near-identical

at `crates/hjkl-bonsai/src/runtime/compile.rs:84-95` and
`crates/hjkl-bonsai/src/runtime/source.rs:173-184, 306-317, 374-385`.

Not a `write_atomic` fit — these publish _directories_ with EEXIST-tolerance —
but four in-crate copies of one 12-line helper, in a crate that already routes
plain file writes through the seam (`runtime/loader.rs:361,370`). **Confidence:
high** (three of four read and compared directly).

## 3. YAGNI

### Y1 (Highest value) — `hjkl-css`: an entire crate with zero consumers, published every release

`crates/hjkl-css` (~90 KB across `lib.rs`, `parse.rs`, `ast`, `resolve`,
`value`) implements a CSS-subset parser to "drive declarative UI styling…pair
with an adapter crate". That adapter (`hjkl-css-gui`) was deleted in the
vim-only pivot (`CHANGELOG.md:338`).

Verified dead: grep for `hjkl-css|hjkl_css` across every `Cargo.toml` and `.rs`
under `crates/` and `apps/`, excluding the crate itself, returns **nothing**.
The only surviving references are the workspace dependency table
(`Cargo.toml:25`) and CI — which still **publishes it to crates.io on every
release** (`.github/workflows/ci.yml:891`). Built, tested, version-bumped and
published for no consumer. **Confidence: high.**

### Y2 — `hjkl-fs` public API with zero consumers

Verified by whole-workspace grep (matches only inside `hjkl-fs` and its tests):

| Symbol                 | Defined                        | Workspace uses |
| ---------------------- | ------------------------------ | -------------- |
| `guard_not_swapped`    | `identity.rs:280` (lib.rs:132) | 0              |
| `hardlink_count`       | `identity.rs:318` (lib.rs:132) | 0              |
| `resolve_under`        | `path.rs:159` (lib.rs:135)     | 0              |
| `owner_only_options`   | `open.rs:109` (lib.rs:134)     | 0              |
| `read_capped_from`     | `read.rs:47` (lib.rs:137)      | 0              |
| `private_state_subdir` | `dirs.rs:61` (lib.rs:131)      | 0              |

Shipped in 0.37.0 for issues #315/#317/#318. Two qualifications that pull in
opposite directions:

- `resolve_under` is **not** speculative — it is the fix for B5, sitting unused
  beside the weaker lexical check it was written to replace. Wire it up, don't
  delete it.
- The rest are well-built primitives with no caller and no identified consumer.
  `hardlink_count` in particular exists to inform a decision (`save.rs:18-20`
  accepts hardlink breakage as a tradeoff) that no code consults it for. That is
  the honest YAGNI half.

`canonicalize_nearest`, `copy_dir_atomic`, `remove_path_all` and
`read_to_string_capped` **do** have callers — though the first three are used
only inside `hjkl-fs` and could be `pub(crate)`. **Confidence: high.**

### Y3 — `hjkl_config::write_default` is dead

**`crates/hjkl-config/src/loader.rs:229-244`.** Zero callers workspace-wide; the
only references are the `lib.rs:33` re-export, doc mentions, and its own test
(`tests/integration.rs:94`). It also uses plain `std::fs::write`, so if it ever
acquired a caller it would be a non-atomic bypass of the seam — which
`crates/hjkl-config/src/write.rs:13-15` explicitly warns against. **Confidence:
high.**

### Y4 — feature flags no workspace consumer enables

- **`hjkl-editor-tui`'s `crossterm` feature** — the workspace dep is
  `default-features = false` (`Cargo.toml:27`) and the sole consumer
  (`apps/hjkl/Cargo.toml:51`) adds no features, so
  `#[cfg(feature = "crossterm")]` (`crates/hjkl-editor-tui/src/lib.rs:189-231`,
  the D5 twin) compiles only when the crate is tested standalone.
- **`hjkl-engine`/`hjkl-editor` `serde` features** — `hjkl-engine` is
  `default-features = false` (`Cargo.toml:28`); no workspace `Cargo.toml` passes
  `features` on it, and `hjkl-editor`'s `serde = ["hjkl-engine/serde"]` forward
  is never enabled. The stated audience ("wasm / no_std hosts") does not exist
  after the vim-only pivot.

**Confidence: medium.** Both are published crates, so an external consumer could
enable them; per the repo's pre-1.0 no-backcompat policy that is not a reason to
keep them, but it is a reason to decide deliberately rather than delete on
sight.

### Y5 (Low value) — `AppConfig` trait machinery with one implementor

**`crates/hjkl-config/src/loader.rs:23-31`** — the trait plus generic
`load`/`load_from`/`load_layered`/`config_path` are instantiated by exactly one
production type (`crates/hjkl-app/src/config.rs:191`). The doc's envisaged
"config.toml, keymap.toml, theme.toml" fan-out never happened; there are in fact
no user-configurable keymaps in the schema at all. Noted because it is the
one-implementor pattern the audit asked about; the indirection is cheap and this
is the lowest priority here. **Confidence: high** on the fact, **low** on it
being worth changing.

## Corrections to claims that did not survive checking

Recorded because a wrong finding costs more than a missing one:

1. **"`decode_macro` silently drops unknown tags"** — false. It emits the tag as
   literal characters (`input.rs:195-214`). The _doc comment_ says "dropped
   silently", which is what the claim was tracking; the comment is stale. That
   is B14, and B6 is stated in terms of actual behaviour.
2. **"The same notation works in config-file keymaps but not `:nmap`"** — false
   premise. There are **no** user-configurable keymaps in the config schema.
   `Chord::parse` serves _built-in_ bindings (`keymap_build.rs`) and which-key
   notation. B6 drops that framing.
3. **"The live crossterm bridge drops PageUp, so those keys do nothing"** —
   unconfirmed and probably wrong: the app intercepts PageUp/PageDown before the
   bridge in insert mode (`event_loop.rs:145-152`). Downgraded to D5, a
   duplication finding with an explicit note that no behavioural loss was shown.

## Not verified

Gaps in this audit, stated plainly:

- **Windows-only paths — not executed** (Linux host, no cross-compilation
  attempted): `crates/hjkl-fs/src/identity.rs:141-215` (the
  `GetFileInformationByHandle` FFI, its `MaybeUninit` handling, the
  `FILE_FLAG_BACKUP_SEMANTICS` directory-handle requirement);
  `crates/hjkl-fs/src/dir.rs:359-371` (`remove_path_all`'s
  `FILE_ATTRIBUTE_DIRECTORY` branch); the `#[cfg(not(unix))]` `Unsupported` arms
  in `atomic.rs:392-400` and `dir.rs:109-117`, which mean a tree containing a
  symlink cannot be copied on Windows at all; and `open.rs:16-28`'s claim that
  confidentiality comes from the containing directory's inherited ACL. All read
  and internally consistent; none run.
- **macOS-only paths — not executed.** Includes a reported reachable panic at
  `crates/hjkl-clipboard/src/backend/macos.rs:248` (`CString::new(s).expect(…)`
  on a `Custom` mime containing NUL, reachable from the public
  `Clipboard::set`). Read as plausible; not confirmed.
- **Clipboard backends requiring a live server — read, not run.** Three reported
  Wayland/X11 findings are recorded here rather than above because I could not
  execute them and would not assert them on a read alone: a stale `source.send`
  desynchronizing the `SCM_RIGHTS` fd queue (`wayland_thread.rs:856-872`,
  claimed permanent wrong-pipe pastes plus an fd leak); INCR-send timeout
  signalled as _success_ via a zero-length property, which ICCCM reads as
  "transfer complete", so a timeout truncates silently (`x11_thread.rs:763-791`,
  same shape on Wayland at `:657-665`); and SELECTION_NOTIFY matched only on
  requestor+property, allowing a late reply to be consumed by the next request
  (`x11_thread.rs:510-525`). The first two look substantive and deserve a
  follow-up on a machine with a compositor.
- **B7's crash path** — the lost clamp is verified; the
  LSP-rename-into-unfocused- split scenario was not built.
- **B8's vim rules** come from `:h J`, not from a live nvim comparison; the
  oracle cannot drive `:` keys.
- **B13's input reachability** — the arithmetic is plainly unguarded, but I did
  not confirm the ex count parser can deliver a value that overflows it.
- **B9's concurrent-writer race** was reasoned about, not raced (needs two anvil
  processes installing the same package simultaneously).
- **The `EXDEV` fallback was exercised only via `/dev/shm`.** A removable volume
  or network mount may differ, particularly around mode preservation; B3's
  reproduction used `/dev/shm` as the source filesystem.
- **Y4's external consumers** — no _workspace_ consumer enables those features;
  I cannot prove no crates.io consumer does.
- **One locking test does not test its name.**
  `crates/hjkl-fs/tests/multi_process.rs:105-120`
  (`shared_locks_do_not_exclude_each_other`) acquires and drops two shared locks
  **sequentially in one process**, which cannot demonstrate the cross-process
  sharing the name promises — and structurally cannot, since the in-process
  layer serializes readers by design (`lock.rs:207-211`). Not a bug; a test that
  provides less assurance than its name implies.

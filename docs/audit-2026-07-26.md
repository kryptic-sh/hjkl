# Audit 2026-07-26 — Implementation Plan

**Source:** Fable 5 whole-workspace audit of hjkl 0.37.0 (14 bugs, 6 DRY, 5
YAGNI). This file is the remediation plan, written to be executed by a delegated
agent item-by-item. Every decision has already been made — do not re-litigate
scope; if an instruction turns out to be impossible as written, stop and report
rather than improvise.

## Ground rules for the implementing agent

1. **One work item = one commit.** Conventional Commits format; the exact
   message is given per item. Stage explicit files only (`git add <file>` per
   file — never `git add -A` / `git add .` / `commit -am`).
2. **Gates after every item**, all must pass before committing:

   ```bash
   cargo clippy --workspace --all-targets -- -D warnings
   cargo fmt --all
   cargo nextest run
   cargo clippy --workspace --all-targets --target x86_64-pc-windows-msvc -- -D warnings
   ```

   The Windows-target clippy is a compile check only; it catches `#[cfg]`-gated
   dead code and Windows-only type errors without a Windows host. If an item
   touches `apps/hjkl` behavior, also run the e2e suite
   (`cargo nextest run -p hjkl --test e2e`) — it is excluded from the default
   run.

3. **Never edit an existing test's expectations to make it pass.** If a test
   fails after your change, the change is wrong (or the test is named in the
   item as one to update — only then).
4. **The nvim oracle must stay ALL-pass** and its case count must not shrink.
   Items that add oracle corpus cases say so explicitly.
5. **Order matters between phases** (later phases assume earlier ones landed).
   Within a phase, items are independent.
6. Work on `main` unless told otherwise. Do not push, tag, or release — commits
   only; the operator handles publishing.
7. Update the **Status** column in the tracking table at the bottom of this file
   as part of each item's commit (`todo` → `done`, or `blocked: <why>`). Run
   `prettier --write docs/audit-2026-07-26.md` after editing it.

## Phase 1 — silent data corruption (do these first)

### B1 — macro recording drops every literal `q`

**File:** `crates/hjkl-vim/src/step.rs:174-180`

The recorder hook:

```rust
if crate::vim_state::vim(ed).recording_macro.is_some()
    && !crate::vim_state::vim(ed).replaying_macro
    && input.key != Key::Char('q')
    && !pending_was_macro_chord
{
    crate::vim_state::vim_mut(ed).recording_keys.push(input);
}
```

The `input.key != Key::Char('q')` clause is redundant for its apparent purpose
and harmful otherwise. The recording-stop `q` never reaches this point
(`begin_step` returns `Err(true)` on it at `step.rs:51-67`), and the `q{reg}`
start chord is excluded by `pending_was_macro_chord` (`step.rs:69-72`). The only
`q`s the clause removes are legitimate: insert mode text (`iquick<Esc>` records
as `iuick<Esc>`) and pending-operator targets (`fq` records as `f`, which
desynchronizes the whole macro on replay because `f` then swallows the next
recorded key).

**Change:** delete the `&& input.key != Key::Char('q')` line. Nothing else.

**Tests to add** (in `crates/hjkl-vim`, alongside the existing macro tests —
find them with `grep -rn "recording_macro\|@a" crates/hjkl-vim/tests` and put
the new ones in the same file/module):

- `macro_records_literal_q_in_insert_mode`: record `qa`, type
  `i`+`quick`+`<Esc>`, stop with `q`. Assert register `a` decodes to exactly
  `iquick<Esc>` (use `encode_macro`/register text). Then replay `@a` on an empty
  buffer and assert the buffer is `quick`.
- `macro_records_q_as_pending_target`: record `qb`, keys `0`,`f`,`q` on a line
  containing a `q`, stop. Assert register `b` is `0fq` and the cursor landed on
  the `q` while recording.

**Commit:** `fix(vim): stop macro recorder from dropping literal q keys`

### B2 — TUI `:w` deletes the file's trailing blank line

**File:** `apps/hjkl/src/app/ex_dispatch.rs:1179` (in the save path)

```rust
let needs_trailing_nl = !body.is_empty() && !body.ends_with(b"\n");
```

The load path strips exactly one trailing newline
(`apps/hjkl/src/app/mod.rs:803`), so a file `"x\n\n"` loads with
`content_joined() == "x\n"`; the `ends_with` clause then decides no terminator
is needed and `:w` writes `"x\n"` — the file shrinks on a no-edit save. Headless
(`apps/hjkl/src/headless.rs:262`) and embed (`apps/hjkl/src/embed.rs:404`)
already use the correct condition.

**Change:** replace the line with

```rust
let needs_trailing_nl = !body.is_empty();
```

matching headless/embed. `byte_count` two lines down already derives from
`needs_trailing_nl`, so it needs no edit.

**Tests to add:** e2e pty test in `apps/hjkl/tests/` (find the existing
`:w`-related e2e tests and follow their harness pattern): create a temp file
with content `"x\n\n"`, open it in the TUI, `:w` without editing, quit, assert
the on-disk bytes are still `"x\n\n"`. Add a second case `"a\nb\n"` asserting it
stays `"a\nb\n"` (regression guard for the unaffected shape).

**Out of scope:** the narrower `"\n"` → `""` case (a file that is exactly one
empty line) affects all three write paths identically and needs a decision on
intended vim-parity behavior first. Do not touch it; it is logged under Deferred
at the bottom.

**Commit:**
`fix(app): make TUI :w preserve trailing blank line like headless/embed`

### B3 — `copy_dir_atomic` fails on any tree containing a read-only file

**File:** `crates/hjkl-fs/src/dir.rs:162-174` (`copy_tree`, regular-file arm)

Current code copies with `std::fs::copy` and then reopens the destination
writable to fsync:

```rust
} else if file_type.is_file() {
    std::fs::copy(&src, &dst)?;
    // ...comment about mode ordering...
    if opts.fsync {
        File::options().write(true).open(&dst)?.sync_all()?;
    }
    apply_file_mode(&dst, opts.mode)?;
```

`std::fs::copy` already applies the **source's** permission bits to the
destination, so for a `0444` source the reopen fails `EACCES`. `opts.fsync`
defaults to `true`, so this is the default path. Reproduced: breaks
cross-filesystem trash (`crates/hjkl-app/src/trash.rs:109`) and anvil installs
(`crates/hjkl-anvil/src/installer.rs:288`), both via `move_atomic`'s `EXDEV`
fallback.

**Change:** never re-open the destination — hold one writable handle for the
whole operation. Replace the regular-file arm with:

```rust
} else if file_type.is_file() {
    // One writable handle for the whole copy: `fs::copy` would stamp the
    // source's mode onto `dst` immediately, making a read-only source
    // impossible to fsync through a fresh write-open. Copy the bytes
    // through handles we own, flush while the handle is still writable,
    // and only then apply the final mode.
    let mut reader = File::open(&src)?;
    let mut writer = File::create(&dst)?;
    std::io::copy(&mut reader, &mut writer)?;
    if opts.fsync {
        writer.sync_all()?;
    }
    drop(writer);
    match opts.mode {
        Some(_) => apply_file_mode(&dst, opts.mode)?,
        None => copy_mode(&src, &dst)?,
    }
```

The `None => copy_mode(...)` arm preserves the documented contract (doc comment
on `copy_tree`, "Regular files carry the **source's** mode") that `fs::copy`
used to provide for free. `copy_mode` already exists in this file (used for
directories); confirm its signature and that it is a no-op or sensible on
Windows before relying on it. Delete the now-stale comment block about
flush-before-mode ordering and replace with the comment shown above. Check
whether `apply_file_mode`'s `#[cfg]` structure means the `match` needs a
`#[cfg(unix)]` split — the Windows-target clippy gate will tell you.

**Tests to add** in `crates/hjkl-fs` (unit tests in `dir.rs` or the existing
integration test file for dir ops — match where the current `copy_dir_atomic`
tests live):

- `copy_dir_atomic_copies_tree_with_readonly_file` (unix-gated): build a tree
  containing a `0444` file, copy with default options (fsync on), assert
  success, content equality, and that the destination file's mode is `0444`.
- `move_atomic_cross_device_tree_with_readonly_file` — only if the existing
  suite already has a cross-device harness (grep for `EXDEV` or `/dev/shm` in
  the tests); if it does, add the read-only-file case to it. If not, skip — the
  unit test above covers the broken arm.

**Commit:**
`fix(fs): copy tree files through owned handles so read-only files fsync`

### B4 — inverse of a linewise delete of the last row does not round-trip

**File:** `crates/hjkl-buffer/src/edit.rs:319-361` (`do_delete_range`,
`MotionKind::Line`)

In the `lo > 0 && hi + 1 == n` branch (hi is the last row), the span actually
removed is `"\n" + lines` — leading separator (`line_to_char(lo) - 1` ..
`len_chars()`). But the recorded inverse is
`InsertStr { at: (lo, 0), text: lines + "\n" }` — trailing separator, at a row
that no longer exists after the delete. Replayed, it clamps and inserts in the
wrong place: `"a\nb\nc"` → delete row 2 → `"a\nb"`; applying the inverse yields
`"a\nc\nb"`, violating the contract at `edit.rs:150` ("Pushing the inverse back
through `apply_edit` restores the previous state"). Latent today (undo is
snapshot-based; the only consumer is the deliberately-unwired multicursor path),
but it is a recorded-wrong Edit and will corrupt text the day multicursor lands.

**Change:** make the inverse in that branch insert the _leading_-separator form
at the end of the new last row:
`InsertStr { at: (lo - 1, <len of row lo-1 after the delete, in chars>), text: "\n" + lines.join("\n") }`.

Constraints, in order of importance:

1. **Read `apply_edit`'s `InsertStr` arm first** and confirm what its column
   means (char offset, not byte, not grapheme) before computing the insertion
   column. Do not assume.
2. The register text handed back to callers (the tuple's `removed_joined`) must
   stay in the trailing-`\n` form — vim's linewise registers are `"c\n"`, and
   existing register tests depend on it. Only the returned `Edit` changes shape.
   Check every caller of `do_delete_range` to confirm which value feeds
   registers before assuming the tuple split is clean.
3. The other two branches (`hi + 1 < n`, and `lo == 0 && hi == last`) round-trip
   today — do not touch them.

**Tests to add:**

- Extend the round-trip property test
  (`crates/hjkl-buffer/tests/proptest_roundtrip.rs:87-93`) to also generate
  `MotionKind::Line` — today it only generates `MotionKind::Char`, which is
  exactly why this shipped. The property (apply → apply inverse → equal) is the
  acceptance criterion; it must pass including last-row and whole-buffer
  deletes.
- One concrete regression test: `"a\nb\nc"`, linewise delete of row 2, apply
  inverse, assert buffer is exactly `"a\nb\nc"` again.

**Commit:** `fix(buffer): correct inverse of linewise delete of the last row`

### B8 — `J` join: implement vim's two no-space exceptions

**File:** `crates/hjkl-vim/src/vim/command.rs:402-407`

```rust
let separator = if !cur_line.is_empty() && !next_trimmed.is_empty() { " " } else { "" };
```

Per `:h J`, no space is inserted when (a) the first line already ends in
whitespace, or (b) the next line (after trimming) starts with `)`. Both missing:
`"foo "` + `"bar"` → `"foo  bar"` (vim: `"foo bar"`); `"foo"` + `")x"` →
`"foo )x"` (vim: `"foo)x"`).

**Change:** extend the condition:

```rust
let separator = if !cur_line.is_empty()
    && !next_trimmed.is_empty()
    && !cur_line.ends_with([' ', '\t'])
    && !next_trimmed.starts_with(')')
{
    " "
} else {
    ""
};
```

This is reachable from `J`, visual `J`, and `:join` — the fix is at the shared
seam, so one change covers all three.

**Tests to add:**

- Unit tests in `hjkl-vim` for both exceptions plus the plain case.
- **Oracle corpus cases** (this is the real acceptance): `J` is a normal-mode
  key, so the nvim oracle _can_ drive it. Add corpus cases joining a line ending
  in a space, a line ending in a tab, and a line whose successor starts with
  `)`. The oracle count must go up and stay ALL-pass. Find the corpus by
  grepping the oracle test for how existing cases are registered.

**Commit:**
`fix(vim): implement J join no-space exceptions (trailing ws, leading paren)`

### D1 + B6 — one parser for `<...>` key notation; fix `:map` mis-parses

**Files:** `apps/hjkl/src/app/keymap.rs:147-169` (`parse_key_sequence`),
`crates/hjkl-engine/src/input.rs:118-214` (`decode_macro`),
`crates/hjkl-keymap/src/chord.rs:231-259` (`Chord::parse` — the complete
parser).

Today three parsers exist and have drifted. The user-visible bug (B6):
`:nmap <Enter> x` binds the seven-character literal `<`,`E`,`n`,`t`,`e`, `r`,`>`
because `parse_key_sequence` only lowercases a subset of tags into
`decode_macro`'s case-sensitive spellings. Worst case: `<C-S-x>` parses as
Ctrl+`S` — a _different valid binding_. `Chord::parse` handles all of it
correctly (`<Enter>`/`<Return>`→CR, `<Escape>`, `<Insert>`, F1–F12, `<S-Tab>`,
stacked modifiers).

**Change (decided approach — app-layer routing, no engine surgery):**

1. In `apps/hjkl/src/app/keymap.rs`, rewrite `parse_key_sequence` so that every
   `<...>` tag is parsed with `hjkl_keymap::Chord::parse` (the app already
   depends on `hjkl-keymap` — verify in `apps/hjkl/Cargo.toml`; if not, add the
   workspace dep). Plain characters outside tags keep their current handling.
2. Write one adapter `fn chord_to_input(chord: &Chord) -> Option<Input>`
   (private to `keymap.rs`) mapping the chord's key + modifier flags onto
   `hjkl_engine::input::Input` (`key`, `ctrl`, `alt`; SHIFT on a letter becomes
   the uppercase char, matching how the engine receives shifted keys elsewhere —
   check `from_crossterm`/existing conversions for the convention rather than
   guessing). Return `None` for chords the engine cannot represent, and surface
   that as a `:map` parse error rather than silently dropping.
3. `decode_macro` itself **stays as-is** (it also serves register/macro
   round-tripping, where literal-emit is correct behavior). Only the
   `:map`/keymap path stops depending on its tag table.
4. `<leader>` handling in `parse_key_sequence` is app-specific — keep it where
   it is, resolved before/alongside tag parsing as it is today.

**Tests to add** (extend `apps/hjkl/src/app/tests/keymap.rs`, which today only
covers `<leader>` and `<CR>`):

- `<Enter>`, `<Return>` both produce the Enter key (same as `<CR>`).
- `<Escape>` == `<Esc>`; `<Insert>`; `<F5>`; `<S-Tab>`.
- `<C-S-x>` produces Ctrl+Shift-x (per the adapter convention), **not**
  Ctrl+`S`.
- A genuinely unknown tag (`<NoSuchKey>`) is a mapping error, not a literal
  binding.

**Commit:** `fix(app): route :map key notation through hjkl-keymap chord parser`
